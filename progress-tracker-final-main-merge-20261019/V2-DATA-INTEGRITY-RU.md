### Автозаполнение

- Сохранены фильтры `user_id`, `exercise_id`, `performed_on <= выбранной даты` и порядок `performed_on DESC, created_at DESC, id DESC`.
- `lastEntryQuery` имеет `staleTime: 0` и `refetchOnMount: "always"`; некорректная/пустая дата не запускает запрос.
- Форма применяет подтверждённый ответ текущего контекста, проверяет дату и отмену сессии. Dirty state защищает отдельно вес, массив подходов и RIR; количество подходов определяется полным массивом повторений.
- После успешного RPC отменяются ранее начатые last-entry запросы и инвалидируются все ключи last-entry/entries сохранённого упражнения этого пользователя, включая другие границы даты. Сервер остаётся источником последней записи: время создания не выдумывается на клиенте.
- При возврате после сохранения `8/8/7/7` форма получает новую запись, а не ранее закэшированные `8/8/7/6`. Следующее упражнение также повторно проверяет собственную историю.
- Вес 0 допустим. При отсутствии истории используются существующие параметры программы; диапазон повторений не превращается в выполненные результаты.
- Исторические заметки раньше не участвовали в повторном заполнении, это поведение сохранено: новая запись получает пустую заметку, введённая заметка черновика сохраняется.
- UUID и неизменный payload retry, double-submit guard, граница аккаунта и toast 3000 мс сохранены. Поздний save не сбрасывает другую форму/операцию.

### Дата и черновики

- Дата текущей сессии хранится в `workout:date:v1:<userId>`; чужая дата не восстанавливается. Нативный input сохраняет DOM-элемент и фокус при изменении даты.
- При выборе упражнения автоматически восстанавливается только отредактированный/pending черновик той же даты. Pristine значения заново берутся из истории, а не из старого автозаполнения.
- Неотредактированное автозаполнение больше не записывает новый черновик в localStorage.
- Для старого отредактированного/pending черновика другой даты показано явное действие «Открыть черновик за …». До его нажатия дата текущего логирования не меняется.
- Перед заменой последнего черновика другой датой его полный объект сохраняется под `workout:draft:v1:<userId>:<exerciseId>:<date>`. Старый ключ v1 остаётся совместимым; массового удаления/преобразования нет. Выбор даты позволяет восстановить соответствующий сохранённый черновик.
- При новом контексте даты создаётся новый UUID. Восстановленная отправленная операция сохраняет прежние UUID, дату и payload; её поля остаются заблокированы для безопасного retry.
- После подтверждения удаляются только объекты с UUID сохранённой операции. Черновики других дат, упражнений и пользователей остаются. Сбой резервного сохранения не заменяет прежний объект.

## PostgreSQL: фактические права и миграция

Выполнен новый read-only запрос каталогов подключённой БД, без чтения содержимого пользовательских строк. Метаданные сохранены вне репозитория: `../workout-v2-stage1-2026-10-15/permissions-before.json`.

У `anon` и `authenticated` есть эффективное TRUNCATE на `program_days`, `program_exercises`, `workout_entries` — шесть подтверждённых разрешений. Прямого ACL для PUBLIC на этих таблицах нет; членства этих двух ролей в других ролях не обнаружены. `service_role` имеет собственные полные grants.

Подготовлен [20261015112617_revoke_workout_truncate.sql](drizzle/migrations/20261015112617_revoke_workout_truncate.sql). Имя сгенерировано локально через Supabase CLI `migration new`, файл включён в существующий Drizzle journal с индексом 5. Нового независимого журнала Supabase в репозиторий не добавлено.

Миграция содержит один `REVOKE TRUNCATE` на трёх явно перечисленных таблицах у PUBLIC, anon, authenticated. Она не меняет DML, service_role, RLS, функции, структуру таблиц или данные и допускает повторное выполнение.

Наличие SQL-привилегии не доказывает удалённую эксплуатацию через обычный PostgREST HTTP CRUD. PostgreSQL исключает TRUNCATE из защиты RLS: [официальная документация](https://www.postgresql.org/docs/current/ddl-rowsecurity.html). Различие явных и унаследованных прав проверялось по [документации Supabase](https://supabase.com/docs/guides/troubleshooting/custom-role-inherits-privileges-that-were-not-explicitly-granted-ddaa1c).

### Порядок отдельного применения

1. Подтвердить целевой проект и применённые миграции 0000–0004; пустой Supabase migration list не является основанием повторять старые миграции. Не запускать `drizzle-kit push`.
2. Выполнить [workout-privileges-preflight.sql](scripts/workout-privileges-preflight.sql) в read-only режиме на целевом окружении. Сохранить ACL, effective privileges, membership и default privileges. Проверить владельца таблиц и отсутствие неожиданного наследования TRUNCATE.
3. В разрешённом staging проверить миграцию и обычные CRUD/RPC с настоящими JWT двух тестовых пользователей. Локальные проверки: `npm run test:db`.
4. **Получить отдельное подтверждение перед production-применением.** Затем владелец таблиц/уполномоченная роль выполняет только новый SQL-файл в транзакции с ограниченным `lock_timeout` и `statement_timeout`, например 5 и 30 секунд. При ошибке — ROLLBACK; не расширять grants автоматически. Миграция не требует backfill.
5. Повторить read-only preflight: effective TRUNCATE у anon/authenticated должен быть false для всех таблиц, прямого PUBLIC TRUNCATE быть не должно; service_role и необходимые DML должны совпадать с исходными метаданными. Проверить пользовательские CRUD/RPC и неизменность истории.

**Статус:** применено только к изолированной PGlite/PostgreSQL в памяти с синтетическими пользователями. Production не изменена; B09 нельзя считать закрытой в работающей БД до отдельного применения и проверки.

## Остаточные риски

1. B09 остаётся в production до отдельного согласованного применения. Этот минимальный SQL отзывает только TRUNCATE: REFERENCES/TRIGGER/MAINTAIN и прочие избыточные grants не нормализуются в этом этапе.
2. Default privileges владельцев postgres/supabase_admin по-прежнему могут выдавать TRUNCATE будущим таблицам. Их изменение затронет другие объекты/создателей и требует отдельного анализа; новые таблицы должны явно нормализовать ACL.
3. B01 (frozen lockfile/dependency audit), B02 (устаревшие release E2E) и остальные B05–B08, B10–B13 не входят в этот этап. Общий вердикт релиза остаётся NO-GO.
4. Настоящие JWT, staging CRUD, production-применение, конкурентные PostgreSQL-соединения и физический iPhone не подтверждены.
5. localStorage ограничен квотой и может быть очищен устройством. Полной синхронизации/разрешения одновременного редактирования одного черновика несколькими вкладками нет. Черновики иных дат сохраняются без автоматического TTL, чтобы не удалять ввод без действия пользователя.
