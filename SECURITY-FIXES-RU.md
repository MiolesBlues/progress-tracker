## Что исправлено

**A01.** Все персональные ключи React Query имеют префикс `['user', userId]`; запросы дополнительно фильтруются по владельцу и получают `AbortSignal`. Отдельный store сессии синхронно сообщает React об изменении идентичности, отменяет запросы и удаляет персональный кэш. Приватный компонент не отображается, пока проверенный маршрутом пользователь не совпадает с текущей сессией. Смена поколения сессии пересоздаёт формы. Поздние ответы отменённых запросов и старых сохранений не обновляют новую сессию. Выход скрывает формы до завершения сетевого запроса; повторные события того же пользователя, включая `TOKEN_REFRESHED`, не очищают кэш/черновик и не запускают invalidation.

**A02.** Экран программы заменён интерфейсом персональных дней. Устаревшие `DAYS`, `DayId`, `Exercise.day` не возвращены. Используются `program_days.id` и `program_exercises.day_id`. При пустой программе onboarding вообще не передаёт необязательный `_template`; строгие настройки TypeScript сохранены.

**A03.** Реализованы добавление и переименование дней, архивирование/восстановление, перестановка, ограничение 1–7 активных дней. Можно создать, переименовать, архивировать/восстановить упражнение, перенести его в активный день, изменить порядок, рабочий вес, число подходов и диапазон повторений. Все изменения владельца ограничены RLS и явным `user_id` в клиентских операциях.

Перестановки выполняются атомарными RPC с проверкой полного списка, владельца и отсутствия повторов. Новая миграция сериализует изменения состава/порядка программы и первичную настройку по пользователю. Серверный триггер запрещает восьмой активный день, восстановление сверх лимита и архивирование последнего активного дня. Применение миграции само по себе не изменяет существующие строки.

Архивирование обновляет только `archived_at`, перенос — упражнение по его UUID. Существующие `workout_entries`, их день и снимок названия не переписываются. Упражнения с `NULL day_id` видны отдельно; день назначается только явным выбором и сохранением. Аналитика позволяет выбрать и такие упражнения, включая архивные.

## Production и остаточные риски

- Миграция `0003_program_management.sql` подготовлена и проверена локально, **в production не применена**. Новые RPC порядка и серверные ограничения требуют её отдельного согласованного применения перед использованием новой версии приложения.
- Фактическое количество production-строк с `NULL day_id` не установлено: доступа к данным авторизованного пользователя/БД в этой сессии нет. Подготовлен отдельный read-only `scripts/program-preflight.sql` для проверки упражнений, истории и количества активных дней. Его результаты нужно просмотреть перед согласованием миграции; автоматического backfill нет. Для полного списка всех владельцев нужен соответствующий операторский доступ; обычный пользователь видит только свои строки через RLS.
- Проверки Auth выполнялись с подменёнными событиями/сетевыми ответами, SQL — на локальной PostgreSQL в одном подключении. Реальные JWT двух аккаунтов, несколько вкладок, конкурентные транзакции нескольких подключений и Safari/iPhone требуют staging-проверки. Production RLS/grants и соответствие применённых миграций не подтверждались.
- Остальные пункты A04–A17 не входят в этот этап. В частности, остаются исходные проблемы автозаполнения при обычном refetch, валидации тренировочных записей, идемпотентности сохранения, пагинации и зависимостей. Успешная сборка не означает готовность всего приложения к публичному запуску.
- Merge, push, deploy и изменения production-данных не выполнялись. Появившаяся во время работы отдельная вложенная папка Next.js сохранена и исключена из коммита.
