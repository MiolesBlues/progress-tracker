# Phase 4 — product hardening и data lifecycle

## PT-14: удаление аккаунта

### Инвентарь текущих личных данных

| Таблица                              | Владелец                      | Текущее поведение удаления                                                                |
| ------------------------------------ | ----------------------------- | ----------------------------------------------------------------------------------------- |
| `program_days`                       | `user_id`                     | Архивация; прямое удаление недоступно browser-роли                                        |
| `program_exercises`                  | `user_id`                     | Архивация; отдельный подтверждённый RPC удаляет упражнение только из архива и его историю |
| `workout_entries`                    | `user_id`                     | История; ограничивающие FK защищают связи с программой                                    |
| `workout_entry_sets`                 | `user_id`, `workout_entry_id` | Составной FK к записи; удаляется вместе с записью или упражнением                         |
| `workout_entry_operations`           | `user_id`, `id`               | Retry ledger; FK к `auth.users` с `ON DELETE CASCADE`                                     |
| `workout_entry_operation_tombstones` | `user_id`, `id`               | Технический запрет повторного использования удалённых UUID; FK с `ON DELETE CASCADE`      |
| `workout_entry_set_tombstones`       | `user_id`, `set_id`           | Технический запрет повторного использования UUID подхода; FK с `ON DELETE CASCADE`        |
| `training_template_applications`     | `user_id`                     | Метаданные одноразового применения шаблона; не содержит шаблонный каталог                 |

`training_exercise_catalog`, `training_templates`, `training_template_days` и
`training_template_slots` — общий опубликованный каталог, не принадлежащий
пользователю; удалять его при удалении аккаунта нельзя. Некоторые legacy личные
таблицы не имеют FK на `auth.users`, поэтому удаление Auth-пользователя само по
себе не гарантирует удаление всех данных. Отчёт-схема уже имеет read-only
проверку таких связей в [account-data-preflight.sql](../scripts/account-data-preflight.sql).

### Предлагаемый контракт (требует продуктового утверждения)

Предлагаемый безопасный default: запрос подтверждения аккаунта удаляет все его
личные данные и резервные/технические записи после отдельного подтверждения
пользователем; восстановление не обещается. Перед запуском операция проверяет
владение и orphan-состояние, затем удаляет в одной транзакции все личные
`workout_entries` (тем самым sets), `program_exercises`, `program_days`,
applications и operation/set tombstones. Записи ledger/tombstone удаляются только
в рамках полного удаления той же учётной записи. Общий шаблонный каталог не
затрагивается. Удаление программы/упражнения через archive RPC остаётся отдельной
операцией со своим подтверждением и не является удалением аккаунта.

Этот default не утверждён владельцем продукта. В Phase 4 не добавлены удаляющий
RPC, auth-delete hook, UI, миграция или hosted операция. Это предотвращает
необратимое изменение retention policy. Прежде чем реализовать механизм, нужно
утвердить удаление тренировочной истории, срок хранения резервных копий и
обработку записей, удалённых из auth, но оставшихся в legacy таблицах. Локальные
PGlite lifecycle-тесты допустимы после утверждения точного контракта.

## PT-12: Leaked Password Protection

Read-only сведения Supabase подтверждают, что Production `ProgressTracker`
и staging-проект принадлежат организации плана `free`; параметр Auth защиты
утёкших паролей MCP-представлением проекта не раскрывается. Официальная
[документация Supabase Password Security](https://supabase.com/docs/guides/auth/password-security)
указывает, что настройка находится в Auth settings и доступна на Pro и выше.
Следовательно, текущая возможность заблокирована планом Free; Auth-параметры не
изменялись. После отдельного повышения плана/доступа владелец должен включить
Auth → Password Security → Prevent the use of leaked passwords и подтвердить
состояние в настройках проекта. `authMessage` подготовлен к ошибке compromised /
leaked password. Настройка не проверялась на hosted Auth, тест реального отказа
скомпрометированного пароля невозможен без включённой функции.

## PT-19: продуктовые инструкции

Signup-триггер по умолчанию удалён миграцией `0002`; программа создаётся в
onboarding, шаблон Upper/Lower необязателен. Архивирование и отдельно
подтверждённое постоянное удаление — разные действия. История сохраняется при
архивировании дня; permanent exercise delete удаляет историю упражнения.
Production миграции проходят через release contract и отдельное разрешение;
локальный SQL не означает, что hosted схема обновлена.
