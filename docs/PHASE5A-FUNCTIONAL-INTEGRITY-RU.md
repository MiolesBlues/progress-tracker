# Phase 5A — функциональная целостность

## PT-07: создание элементов программы

День и упражнение получают UUID и неизменный payload до первого INSERT. Pending
операция хранится в localStorage в области пользователя и типа объекта. После
неоднозначного ответа UI сохраняет форму и повторяет тот же UUID и payload, в
том числе после remount. INSERT использует существующий первичный ключ UUID;
после duplicate/error клиент читает объект только с id и user_id текущего
владельца и подтверждает retry только при точном совпадении payload. Чужая строка
невидима через RLS, а конфликт ID не приводит к UPDATE или перезаписи.

Миграция не нужна: таблицы уже имеют PK на id, RLS на владельца и owner policies
на INSERT/SELECT. Hosted ACL/RLS не менялись. При ошибке хранилища запрос не
отправляется. Новый pending snapshot блокирует редактирование его полей до
подтверждения, чтобы retry не изменил первоначальную операцию.

## PT-11: переключение аккаунта во время мутации

Вызов сохраняет signal и поколение сессии аккаунта A. SessionStore отменяет
сигнал и удаляет user cache при смене identity. Устаревшее завершение не закрывает
редактор, не показывает success/error toast и не пишет данные A в cache B.
Серверный запрос создаётся с исходной сессией; локальный тест фиксирует owner,
ID записи и уже отменённый signal перед поздним ответом.

## PT-15: ошибки и локализация

Известные операции создания используют коды unknown, conflict, rejected и
storage; тексты известны обеим локалям. Для неизвестного английского error
используется безопасное общее сообщение, чтобы не показать SQL, токены или
внутренние детали. Известные русские сообщения аутентификации, сохранения,
восстановления, мутаций и шаблонов остаются в typed translation catalog.

## PT-16: границы производительности

Текущие точные Progress и weight-sort Records сохраняют полную историю, полные
approach данные, историю RIR, warmup exclusion, архивные записи и предыдущие
сравнения. Локальный benchmark использует детерминированный fake Supabase adapter
с серверным page cap 1,000; это измеряет число adapter requests, строк
результата и client elapsed, но не сетевую задержку или query plan PostgreSQL.
На 100 × 20 fixture передаются 2,100 строк (100 parents + 2,000 sets), на 1,200
× 2 — 3,600 строк. Запросы и elapsed печатаются тестом в его verbose выводе.
В измерении: 9 запросов и 169 ms для 100 × 20; 17 запросов и 266 ms для
1,200 × 2. Локальная сортировка по весу заняла соответственно 12 и 59 ms.
Это in-process benchmark на fake adapter; задержка процесса и таймеров не является
сетевым latency или PostgreSQL benchmark.
Численные метрики сравниваются с прежней pure reference реализацией; включены
RIR, warmup, архивный день, duplicate timestamps и изоляция второго пользователя.

Weight sort и Progress не переписаны на сервере: произвольный выбор старой
сессии и её точных предыдущей сессии/недели требует расширенного RPC и изменения
UI-пагинации списка сравнений. В Phase 5A миграция и RPC не добавлены, так как
без совместимого hosted capability их использование нельзя подтвердить.
Приложение и локальная схема остаются без нового migration gate. Текущая цена:
полная выборка всех записей и подходов, рост памяти и времени пропорционально
размеру истории. До серверного RPC не следует заявлять масштабируемость этих двух
режимов.

## Проверки и ограничения

Component tests покрывают lost response после commit для обоих типов создания,
повтор после remount, два submit при задержанном ответе, один UUID/объект,
конфликт payload, одинаковые имена разных пользователей и account switch.
Session integration test покрывает поздний workout-set mutation для A после
переключения на B.

Финальные проверки: Vitest — 32 файла, 304 passed; PGlite/SQL — 61 passed;
toolchain — 13 passed; typecheck, lint, format, schema preflight, production
build, bundle scan, Wrangler runtime smoke и dependency checks прошли.
Полный Playwright прогон — 156 passed, 5 predeclared skipped, 1 сначала failed
из-за текста для SQL `22023`. После исправления точечный B12 Chromium прошёл
1/1, B12 WebKit и четыре новые PT-07 E2E сценария прошли в полном прогоне.
Новые browser tests используют mocked Auth/HTTP и не подтверждают реальные
hosted JWT/RLS. Запуск frozen install не менял lockfile.
Hosted staging/prod и production Auth не изменялись.
