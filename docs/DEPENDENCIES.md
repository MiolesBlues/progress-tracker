The first five packages were updated with `bun update shell-quote brace-expansion js-yaml nanoid source-map-js --ignore-scripts`, which updated transitive versions within allowed ranges. Direct framework/React/TanStack dependencies were not broadly upgraded. `audit fix --force` was not run.

At review time, stable drizzle-kit 0.31.11 still used the legacy esm-loader with `esbuild ~0.18.20`. The project therefore used a **parent-scoped**, not global, override to 0.25.12. Core-utils calls `transform`/`transformSync`, not `serve`; `scripts/toolchain.test.mjs` checked the required parameters and results for those APIs. Drizzle `check --config=drizzle.config.ts` also loaded its TypeScript config and checked the journal without connecting to a database. TypeScript, SQL/unit tests, and production build covered remaining compatibility. Reassess the override if the legacy loader is updated or removed; Bun 1.4.3 records it in lockfile v3 ([Bun override docs](https://bun.com/docs/pm/overrides)).

Existing `rolldown: 1.2.1` remained pinned as part of the build preset/Vite baseline. No global esbuild override was added. CLI, launch-editor, ESLint, and Drizzle should not be exposed as application network endpoints; production runs the built artifact, not a dev/preview server. The source review found no public route passing workout input into shell/YAML/glob/custom-generator functionality. This is code reachability analysis, not proof that every future hosting configuration is safe.

A clean installation review found an older nested esbuild copy persisted in existing `node_modules` after the first update even though the lockfile audit was clean. Reinstalling from the frozen lockfile and checking the actually resolved version resolved the mismatch. The original `node_modules` was preserved locally in ignored `.release-node-modules-backup`; user data was unchanged.
