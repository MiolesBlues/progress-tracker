# Приёмка V2 на настоящем Supabase

Исторический план V2. Актуальная read-only сверка 16 октября подтверждает, что B09/B12 уже применены; не повторять перечисленные ниже защитные миграции на действующем Supabase. Текущий порядок и приёмка pending deletion SQL: [STAGING-V3-RU.md](STAGING-V3-RU.md).

Этот план не разрешает запись в production. Сейчас доступен только действующий `ProgressTracker`, development branches отсутствуют. Все выполненные удалённые проверки были read-only. Локальные PGlite/PostgreSQL и мокированный HTTP не заменяют следующие шаги.

## 1. Зафиксировать окружение и исходное состояние

1. Владелец предоставляет отдельный тестовый проект без реальных тренировок и явно подтверждает его назначение. Зафиксировать project ref, URL, PostgreSQL version, Git SHA, browser и время. Не определять цель только по локальному CLI project_id.
2. Проверить совпадение frontend/server URL и publishable key. Secret/service-role ключ допустим только в доверенном серверном окружении, никогда в VITE, браузере, trace или Git. JWT и пароли тестовых пользователей не включать в отчёт.
3. Выполнить [release-schema-preflight.sql](../scripts/release-schema-preflight.sql) и [workout-privileges-preflight.sql](../scripts/workout-privileges-preflight.sql). Это транзакции READ ONLY: каталоги и флаги нарушений, без экспорта тренировок.
4. Сверить колонки/nullable, CHECK, FK владельца, индексы, RLS и политики, триггеры, аргументы/defaults/returns четырёх RPC с SQL и `src/integrations/supabase/types.ts`. RPC — SECURITY INVOKER; anon EXECUTE запрещён, authenticated разрешён. Проверить signup-trigger: не должно быть старого автоматического seed.
5. Сверить journal из `drizzle/migrations/meta/_journal.json` с фактическими каталогами и журналом целевой БД. Пустой Supabase migration list не означает пустую схему. **Не переисполнять 0002 и не запускать drizzle-kit push.** Для исходной схемы текущей удалённой БД тела восьми функций совпали с 0000–0004; это не подтверждение применения трёх новых файлов.

## 2. Репетиция подготовленных миграций

На согласованном staging сначала получить backup и подтвердить восстановление в другом пустом проекте/БД. Затем применить только отсутствующие и проверенные файлы в порядке journal:

- `20261015112617_revoke_workout_truncate.sql` — этап 1, отзыв TRUNCATE.
- `20261015144732_guard_new_exercise_day.sql` — этап 3, атомарная проверка создания упражнения в активном дне.
- `20261015144758_restrict_workout_table_grants.sql` — этап 3, только SELECT/INSERT/UPDATE для authenticated на трёх таблицах; PUBLIC/anon без доступа, service_role не меняется.

Каждый файл применить транзакционно с ограниченными `lock_timeout` / `statement_timeout` (например 5/30 секунд). При ошибке — ROLLBACK и анализ, без автоматической выдачи дополнительных прав. До/после сравнить историю, RLS, service_role и необходимые операции. Файлы не переписывают строки и допускают повторное выполнение. Существующие NULL day_id и NOT VALID CHECK не исправлять автоматически.

Повторить оба preflight. Для PUBLIC/anon/authenticated не должно быть TRUNCATE/REFERENCES/TRIGGER/MAINTAIN; authenticated имеет SELECT/INSERT/UPDATE, не DELETE. Проверить прямой SQL под каждой ролью, включая PUBLIC через роль-пробу: TRUNCATE должен завершаться permission denied **только на синтетических staging-таблицах**. Не выполнять destructive-пробу в production даже с намерением ROLLBACK.

Отдельно владельцу оценить default privileges `postgres` / `supabase_admin`, наследование и служебные интеграции. Подготовленный SQL намеренно ограничен тремя существующими таблицами: creator-wide defaults могут затронуть другие объекты. Для новых таблиц явно нормализовать ACL и включать RLS. Наличие TRUNCATE само по себе не доказывает exploit обычного PostgREST HTTP CRUD: [PostgreSQL о границах RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

## 3. Настоящие Auth и JWT двух пользователей

1. Зарегистрировать A и B через приложение с разными контролируемыми email; проверить несовпадение/пустое подтверждение до signUp и реальное email confirmation. Проверить разрешённые redirects `/workout` и `/auth`, Google consent/cancel/error, rate limits и повторный вход. Confirmation не отправляется на сервер.
2. Получить обычные пользовательские JWT A/B. Не использовать service_role для проверки изоляции. В HTTP передавать publishable `apikey` и `Authorization: Bearer <JWT>`; JWT хранить только локально в защищённом окружении.
3. Для A/B создать разные программы с 1–7 днями и упражнениями, сохранить разные результаты и dirty drafts. Reload, logout, A→B→A, refresh токена того же пользователя, задержанный last-entry/save после смены аккаунта.

| Операция                                                                       | Ожидаемый результат                                           |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| JWT B: GET program_days/program_exercises/workout_entries с user_id или UUID A | Пустая выборка, без строк A                                   |
| JWT B: PATCH строки A с `Prefer: return=representation`                        | Нет изменённых строк A; сравнить исходные значения от имени A |
| JWT B: INSERT с user_id A                                                      | Отказ RLS; нет созданной строки                               |
| JWT A: INSERT/save с exercise_id B или day_id B                                | Отказ FK/серверной проверки; нет истории с чужой связью       |
| JWT A: повтор setup при существующей программе                                 | Отказ, прежние UUID/названия/история сохранены                |
| JWT A: reorder с неполным, дублированным, архивным или чужим UUID              | Отказ всей операции; прежние позиции сохранены                |
| JWT A: save_workout_entry дважды с одним UUID и одинаковым payload             | Тот же UUID, ровно одна строка                                |
| Тот же UUID с другим payload или JWT B                                         | Отказ; первоначальная строка не изменена                      |
| Новый UUID, то же упражнение/дата                                              | Разрешена отдельная сессия                                    |
| Анонимный API и RPC                                                            | Нет доступа к данным/четырём RPC                              |

Коды SDK/PostgREST могут различаться по месту отказа. Критерий — отсутствие чужих/частичных изменений, корректный SQLSTATE там, где он доступен, и понятная ошибка UI; успешный HTTP с пустой выборкой не считать доказательством успешного UPDATE.

## 4. Цепочки и конкурирующие соединения

- Регистрация → подтверждение → onboarding → личные дни; повторный вход не пересоздаёт программу.
- Создание/переименование/порядок/архив/восстановление дней и упражнений; выбранный UUID сохраняется отдельно A/B и переключается с архивного дня. Пустой или длинный ввод не теряется при ошибке.
- Тренировка: 50 кг, 8/8/7/6, RIR 2 → изменить последний подход на 7 → save → toast около 3 секунд → собственная история следующего упражнения. Вернуться к первому: 8/8/7/7. Date сохраняется, будущая запись не автозаполняется, поздний ответ не заменяет dirty-поля.
- Потеря ответа после commit → retry/reload → один UUID/одна строка. Ошибка INSERT сохраняет все значения.
- «Записи»: день/упражнение, архив и «Без назначенного дня», сегодня/7/30/all, одинаковый вес и несколько сессий за день; UI по 20 строк, полнота серверной пагинации при maxRows меньше размера страницы.
- «Прогресс»: выбранная сессия, независимая предыдущая сессия и календарная неделя, вес/reps/volume, нулевой baseline, RIR/подходы, обе границы дат, отсутствие будущих результатов.
- Два SQL-соединения с ролью authenticated: (1) архивирование дня удерживает owner-lock, INSERT ждёт и затем отвергается; (2) INSERT удерживает lock, архивирование ждёт commit создания; (3) одновременный retry одного UUID возвращает одну строку; (4) setup/добавление восьмого дня/reorder не создают частичного результата. Проверить на версии PostgreSQL staging, не только локальной 18.6.

## 5. Backup / restore и выпуск

Владелец проверяет доступность и давность managed backup/PITR, тариф/retention, шифрование и ограничение доступа. Восстановить в **отдельный пустой тестовый проект**, сопоставить число/хэши строк трёх таблиц, FK/CHECK, RLS/ACL, функции/триггеры, индексы и журнал. Для Auth отдельно проверить поддерживаемую Supabase процедуру восстановления и вход тестовых аккаунтов. Локальный pg_dump синтетической БД этого не подтверждает. [Документация backups](https://supabase.com/docs/guides/platform/backups).

На физическом iPhone проверить Safari/VoiceOver, клавиатуру, safe-area, PWA, длинные имена и native date input. Playwright Chromium/WebKit 320/375/390/430 px — дополнительное доказательство, не замена устройства. Повторить наблюдение R1 на медленном API с весом до/после reload.

Перед публикацией отдельно подтвердить hosting runtime/env, HTTPS/headers, redirects и неизменность выбранного Supabase-проекта. Security Advisor сейчас сообщает WARN о выключенной leaked password protection: оценить и согласовать настройку по [документации Auth](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection); автоматического изменения конфигурации нет.

Итоговая приёмка содержит SHA, версии миграций, только обезличенные результаты PASS/FAIL/NOT RUN и ссылки на артефакты. Пока отсутствуют критические настоящие JWT, backup restore и отдельное разрешение production grants/B12, решение — NO-GO. Production-применение, merge, push и deploy требуют отдельного действия владельца.
