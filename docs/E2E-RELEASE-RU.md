# Приёмка релиза: два отдельных пользователя

## Автоматическая проверка UI

`bun run test:e2e` запускает приложение локально с фиктивным Supabase URL `workout-e2e.invalid`, Chromium/WebKit и перехватом всех внешних запросов. Реальный Auth/API не вызывается. Сценарии актуализированы под подтверждение пароля, диалог добавления упражнения без дня/веса, редактор без веса, непрерывное логирование с toast и отдельный экран «Записи». Сохранены проверки onboarding, черновиков, потерянного ответа/retry с одним UUID, архива/истории, графиков, A→B→A и Retry загрузки. Добавлены свежесть last-entry и дата следующего упражнения из этапа 1, фильтры дневника и стабильная сортировка одинаковых весов.

На 320/375/390/430 px в обоих движках проверяются overflow, настоящая форма date/weight и отдельный fixture production CSS, Select, модальные окна, dock/toast, клавиатурный и мышиный drag. TouchSensor проверяется синтетическими DOM-событиями с массивами touches, удержанием и движением по кадрам, включая первый→последний день, reload и сетевой отказ. Конструктор Touch в Windows WebKit недоступен, а публичный Playwright Touchscreen API поддерживает только tap. Поэтому touch-сценарий проверяет обработчики приложения, но не доверенный нативный жест ОС. Это не физический iPhone/системная клавиатура/VoiceOver. Перед новым drag тест ждёт подтверждения предыдущего сохранения; hardening-сценарий отдельно подтверждает недоступность activator во время задержанного rename и его включение после ответа.

V2 включает 38 браузерных проверок: дополнительно сохранение/fallback выбора дня, scoped ошибки редактора, архив/восстановление, NULL-day история, страницы дневника, разделение текста Auth, тёмный toast и отказ создания при серверном конфликте активности дня. Итоговые результаты и границы доказательств: [RELEASE-READINESS-V2.md](../RELEASE-READINESS-V2.md). Реальная приёмка и подготовленные миграции: [STAGING-V2-RU.md](STAGING-V2-RU.md).

Нужны Node.js 24, Bun 1.4.3, `bun install --frozen-lockfile --ignore-scripts`, затем `bun run build` (CSS fixture требует production-артефакт) и `bunx --no-install playwright install --with-deps chromium webkit`. Скриншоты/trace и JSON находятся в `test-results/`, HTML в `playwright-report/` (не коммитятся). CI запрещает `.only`, не повторяет падения автоматически и не подавляет ненулевой exit code; отчёты сохраняются и при неуспехе.

Это E2E интерфейса с подменённым backend: имитация не подтверждает проверку JWT, RLS, SMTP, OAuth redirects или конкурентные транзакции настоящей БД. SQL-проверки выполняются отдельно на PGlite. Для публичного релиза обязательна следующая приёмка на изолированном staging с настоящим Supabase.

## Предусловия staging

Отдельный Supabase-проект без пользовательских production-данных; согласованно применённые 0000–0004 и отдельно разрешённая миграция B09 из первого этапа V2; два тестовых email A/B; проверенная доставка подтверждения email и allowlist redirects. Убедиться, что URL не production. Сохранить commit SHA, версию схемы, браузер, viewport, время и результаты каждого сценария. Пароли, JWT, email реальных пользователей и service-role ключи не включать в отчёт/trace. Для permission-проверок использовать обычные JWT A/B, никогда service-role в браузере.

## Блокирующие условия

Не ставить GO, пока не подтверждены реальные JWT/RLS двух пользователей, соответствие staging/production-схемы, read-only диагностика старых данных, backup restore и критические сценарии выше. Отсутствующие проверки помечать «не выполнено», не PASS. Production-миграция, публикация приложения и merge в main — отдельные действия с подтверждением пользователя.
