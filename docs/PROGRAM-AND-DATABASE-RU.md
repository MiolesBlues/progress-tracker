# Персональная программа, история и аналитика

## Связи и изменения

`program_days.id` — UUID пользовательского дня; `user_id` — владелец. Допустимы 1–7 активных дней, произвольное имя до 60 символов, порядок `position`, архив `archived_at`. Регистрация сама программу не создаёт. `setup_program(_names, _template?)` создаёт выбранные дни атомарно; `upper_lower` — необязательный шаблон.

`program_exercises.day_id` ссылается на день того же владельца. Упражнение имеет имя до 100 символов, порядок, рабочий вес, целевые подходы/повторения, пример повторений и архив. Перенос меняет только текущую программу. Старый текстовый столбец `day`, если остался в БД, не используется клиентом. `NULL day_id` показывается отдельно: назначение возможно только явным действием пользователя. Автоматического backfill в исправлениях нет.

В UI редактора программы рабочий вес не показывается и не обязателен; поле модели остаётся совместимым с прежними программами и fallback автозаполнения. Выбор активного дня программы сохраняется отдельно по пользователю, архив доступен в управлении. Дневник включает группу «Без назначенного дня», в том числе архивные упражнения, и показывает по 20 записей без ограничения полноты серверной загрузки.

`workout_entries` содержит UUID операции/записи, владельца, UUID упражнения, дату `performed_on`, время создания, вес, массив повторений, RIR/заметки и исторический снимок `day_id/day_name`. Новые записи разрешены только для активных упражнения и дня; сервер проверяет владельца и соответствие дня упражнению, определяет снимок названия. Последующие переименование/архивирование/перенос не меняют историю. RESTRICT и составные FK запрещают потерю/перепривязку истории. Отдельная миграция `20261015202500_archived_object_deletion.sql` добавляет ограниченные RPC для удаления только архивных объектов: удаление дня обнуляет ссылки `day_id`, сохраняя упражнения и исторический снимок `day_name`; удаление упражнения удаляет только его записи. До отдельного применения этой миграции в выбранной БД кнопки удаления не работают.

Сохранение через SECURITY INVOKER `save_workout_entry` использует UUID, созданный до первой отправки и записанный в локальный черновик. Повтор того же payload возвращает прежний ID; другой payload с тем же ID отклоняется. Повтор уже сохранённой операции работает и после архивирования. Новый осознанный результат получает новый ID; уникальности `(exercise_id, performed_on)` нет.

## Ограничения ввода

Вес обязателен: 0–2000 кг, до двух знаков после запятой; пустая строка не равна нулю. Повторения — массив из 1–20 непустых подходов, целые числа 0–2147483647. Последовательность `8-8-7-6` в одном поле отклоняется с объяснением; вводится четыре поля. RIR необязателен, 0–10 с одним десятичным знаком; заметки до 1000 символов. Десятичная запятая поддерживается для веса/RIR. CHECK для массива проверяет размерность, нижнюю границу, количество и отсутствие NULL/отрицательных элементов; ограничения действуют также для `example_reps`.

## Смысл аналитики

- Порядок записей: `performed_on`, затем `created_at`, затем `id`, по возрастанию. При одинаковой дате несколько записей считаются отдельными сессиями. При отсутствии времени фактического выполнения порядок внутри дня определяется временем создания, не выдуманным временем тренировки.
- Предыдущая сессия — ближайшая строго более ранняя запись того же упражнения и пользователя относительно выбранной записи.
- Предыдущая календарная неделя — понедельник–воскресенье перед неделей выбранной даты. Для сопоставления **одной сессии с одной сессией** берётся последняя запись того же упражнения за эту неделю. Это не сумма всей недели. При отсутствии записи сравнение пустое; поиск не уходит в более старые недели.
- Вес: `(новый − прежний) / прежний × 100%`; относительно 0 процент не определяется. Повторения: разность сумм; объём: разность `вес × сумма повторений`. Показываются подходы и RIR обеих сессий. Любая разница количества подходов или разница RIR ≥2 вызывает предупреждение. При пропущенном RIR полнота сопоставления усилия не подтверждена.
- График: локальная календарная дата устройства задаёт верхнюю границу фактически выполненных тренировок; нижняя — `end − (N−1)` для N дней, обе включены. «Всё время» сохраняет верхнюю границу. Внутри дня вес берётся максимальный, повторения/объём суммируются. Дата устройства не определяет сравнения выбранной записи.
- История выбранного упражнения загружается страницами по 250 с точным count и порядком. Если сервер возвращает меньше, следующий offset увеличивается на **полученное** число строк. Программы/архивы также пагинируются. Частичные данные не возвращаются в кэш: ошибка, смена count, повторный ID, отсутствие count или защитный лимит 100000 строк блокируют расчёты и предлагают Retry. UI истории показывает по 20 записей за выбранный период; выбор точки сравнения доступен по полной загруженной истории.
- Offset-пагинация не является транзакционным снимком: одновременная правка без изменения count может остаться незамеченной. Для больших объёмов/частых конкурентных правок нужен серверный snapshot/RPC. Сейчас при выявленном изменении требуется повторная загрузка; предупреждения не заменяют эту будущую гарантию.

## Миграции и эксплуатация

0000 — исходная схема/RLS; 0001 — поля программы и сохранность истории; 0002 — персональные дни и отказ от signup seed; 0003 — управление днями/порядком и блокировки; 0004 — строгие CHECK, снимок дня, идемпотентное сохранение. Journal содержит `20261015112617_revoke_workout_truncate`, `20261015144732_guard_new_exercise_day`, `20261015144758_restrict_workout_table_grants`. Read-only сверка V3 16 октября подтвердила их применение в действующем Supabase с remote timestamps `20261015162555`, `20261015162607`, `20261015162616`; повторять их нельзя. Новая `20261015202500_archived_object_deletion` остаётся локальной и требует отдельной staging-приёмки.

Установленный B12 при INSERT упражнения с ненулевым day_id проверяет активность и владельца под той же транзакционной owner-lock, что и архивирование дня. Существующие NULL-связи и UPDATE архивных упражнений не преобразуются. B09 сузил права только трёх таблиц до SELECT/INSERT/UPDATE для authenticated; PUBLIC/anon и избыточные полномочия удалены, service_role/RLS не менялись этой миграцией. Creator-wide default privileges требуют отдельной оценки. Порядок единственной недостающей миграции и настоящей JWT/backup-приёмки: [STAGING-V3-RU.md](STAGING-V3-RU.md).

Перед согласованным применением: сохранить backup; выполнить `scripts/program-preflight.sql` и `scripts/workout-preflight.sql` в read-only транзакции с нужной видимостью владельцев; сохранить результаты без публикации персональных данных; отдельно решить судьбу NULL-связей и нарушений. NOT VALID из 0004 защищает новые/обновляемые строки, но не исправляет старые. Не выполнять VALIDATE, DELETE, backfill или переисполнение старых миграций без проверки и согласования.

Проверить цепочку 0000–0004 на изолированной копии; migration runner должен учитывать журнал и транзакции, таймауты/блокировки и применять только отсутствующие файлы по порядку. Пустые декларативные Drizzle schema/snapshots не подходят для `push`/автоматической генерации. Затем на staging проверить реальные JWT двух пользователей, grants/RLS, повторную отправку, конкурентные операции и backup restore. Локальные PGlite-тесты с тестовым `auth.uid()` этого не заменяют.
